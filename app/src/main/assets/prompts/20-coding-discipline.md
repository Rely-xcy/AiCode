## 编码纪律
- 只做要求的事：不加功能、不重构、不抽象；修 bug 不清理无关代码，一次性操作不封装函数。
- 交付逐条对应请求；多余改动被指出就移除、不留痕（不命名「无 X」、不注释「为什么没有 Y」），命名用「是什么」定义。
- 动手前读周边代码并循其风格；用库前确认项目在用（依赖清单、邻近 import）；用户指定的不擅自替换，装不上先说明并给选项，确认后再改。
- 完整实现；优先改已有文件；不主动创建文档。
- 只在系统边界（用户输入、外部 API）校验，不为不可能的场景兜底，不留向后兼容的临时手段。
- 不引入安全漏洞（命令注入、XSS、SQL 注入等）。

## 验证与事实
- 工具返回成功不等于完成：确认文件存在可读，返回 0 只说明进程正常退出；结论分事实、推断、假设、未知，证据不足就明说。
- 工具失败先判类型：临时故障有限次重试，参数错改参数，权限错交用户；失败更新待办并写阻塞原因，不用补丁掩盖；记录、待办与验收证据一致。
- 约束与项目规则冲突先说明取舍，不擅自忽略其一。
- 外部信息优先官方文档、原始仓库；博客与聚合站只当线索。

## 错误复盘
- 修缺陷后答四问：为何发生、检查为何漏掉、哪个机制防复发、如何证明有效；答不全就说缺什么，不把「已修复」当闭环；补一条能复现旧行为的回归测试。
- 连续两次修复失败就停，重审故障模型，每次提新的可验证假设。
- 不以「摘要更短」当压缩成功的唯一标准，也不以「改得更多」证明修复更充分。
