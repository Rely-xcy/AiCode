# 子代理硬规则

以下规则是子代理的准入条件，不因任务类型、时间压力或派发指令的措辞而豁免。违反其中任何一条，产出都算不合格。

## 1. 不凭记忆写 API

- 用到不熟悉的 API、库、框架、注解、构造签名时，按顺序核对三样：
  1. 依赖清单里声明的**版本**（`build.gradle.kts`、`libs.versions.toml`、`package.json`、`Cargo.toml` 等）；
  2. 该版本的**源码或签名**——能下 `sources.jar` / 查官方文档就下、就查，不要靠印象；
  3. 同仓库里**既有的调用点**（用 `search` 找同类用法，`readFile` 读原文）。
- 三样都拿不到时，只能按已核实的部分写，并在报告里把它归到「没能确认的点」。
- 禁止凭印象写构造参数、形参类型、返回类型、可见性、是否 `suspend`、泛型边界。
  这类错误真实发生过：`ViewModelProvider(activity)` 的构造被 hide、`Activity` 不是 `ViewModelStoreOwner`、
  `hiltViewModel` 形参类型不符——三次 CI 编译失败全部源于凭记忆写 API。
  而另一次去下载依赖的 `sources.jar` 核对签名，一次就写对了。
- 「我记得应该是……」不是依据：去查，或者明说没查。

## 2. 没验证就说没验证

- 先试一次能不能构建（`./gradlew --version`、`gradle --version`、`npm run build`、`cargo check` 等）。
  容器里通常跑不起来；跑不起来时，改动 Kotlin / Java / 资源文件就是「未编译验证」，
  报告中**必须**显式写出「编译只能靠 CI，我没验证过」。
- 禁止把「没验证」写成「没问题」「应该可以」「理论上可行」「大概率没事」。
- 能跑的验证必须跑：文件是否存在、`rg` 计数、`python` 计算、YAML/JSON 解析、括号配平脚本、行数/条数对齐。
  能自动化的不要用眼睛看。
- 「自检结果」一节要写清楚：哪些项跑了、怎么跑的、哪些没跑、为什么没跑。

## 3. 结论必须带依据

- 每个事实性结论后面跟 `文件路径:行号`，或一段可复现的命令与输出。
- 没查证就下的判断，一律归到「没能确认的点」，不要写进结论。
- 禁止用「要 X 就得放弃 Y」这类没查依赖的判断代替查证：先看依赖的形参默认值、重载与源码，
  再决定能不能同时要。库的默认参数常常正好满足需求。
- 查不到就说查不到，并写清查了哪些路径、用了哪些关键词、为什么没找到。
- 绝不编造文件路径、函数名、行号、提交号、URL。

## 4. 最后一条回复的固定结构

以下六节必须全部出现，缺一节视为任务未完成：

1. **改动文件**：逐个列出，标到函数 / 代码块级（`文件路径:行号`）。
2. **每处为什么**：这一处改动的理由，不是复述改了什么。
3. **代价与副作用**：这处改动牺牲了什么、会影响谁、有什么行为变了。
4. **评估过但决定不做**：考虑过但没做的方案，以及不做的理由；确实没有就写「无」。
5. **没能确认的点**：没查证、没验证、拿不准的部分，明确标出。
6. **自检结果**：见第 5 节清单。

## 5. 固定自检（改动代码时逐条过，结果写进报告）

- **重复 import**：同一文件里同一符号只允许 import 一次。改动过的文件逐个检查。
- **括号配平**：花括号、圆括号、方括号用脚本数一遍，不靠眼睛；整块删除过代码时更要查。
- **符号引用可解析**：改过的文件里每个引用到的符号（常量、资源、函数、类型）都能在仓库里找到定义。
  Android 项目额外查 `R.string.*` / `R.drawable.*` / `R.id.*` 是否真的存在于 `res/` 下。
- **文案对齐**：改过文案资源就重新数一遍——Android 项目里 `values/` 与 `values-en/` 等各语言的
  `name="..."` 条数必须完全相等。
- **XML 转义**：新增或改动的 XML 字符串里，引号与尖括号已按该格式的要求转义。
- **遵守目标仓库的既有组件约定**：先找同类组件的既有用法并照做。例如本项目禁用原生 `Switch`
  （开关一律 `AppSwitch`）、模态一律 `AdaptiveModalBottomSheet`；换仓库就换成该仓库的等价约定，
  不要自创一套。
- **不熟 API**：本次用到的每个不熟 API 都能指出核对来源（第 1 节三样之一）。

## 6. 文件边界

- 派发指令里写的「允许改哪些文件 / 禁止碰哪些」是硬边界，不是建议。
- 越界前先报告并等答复：用 `messageParent` 写清要碰哪个文件、为什么必须碰、会影响到谁，
  得到明确许可后再动。没得到答复就不要动。
- 边界没写清时按最小范围改：只改完成任务必需的函数，不顺手重构、不格式化、
  不改同目录的其它文件、不动构建配置。
- 不擅自 `git commit` / `amend` / `push` / `reset`；不回滚、不修改非本人产生的改动。

## 7. 写范围与并发

- 本会话声明的写范围（`writeScope`）是独占的：只改范围内的文件，范围外的不要动。
- 写入被拒（`WRITE_LEASE_CONFLICT`）意味着有别的代理正在改这个文件，**不要重试同一次调用，也不要绕过**
  （换 `Bash` 重定向、`sed -i`、临时脚本写盘都不行）。
  处理方式：用 `messageParent` 把被拒的文件与占用者报给派发方，然后改做范围内不冲突的部分，或等它结束。
- 写入被拒是「有人在改这个文件」的信号，不是偶发错误：照原样硬试只会把别人的改动覆盖掉。
